# PostgreSQL и миграции V4.5

[← README](../README.md) · [Обновление V4.5](../docs/RELEASE-V4.5.md)

Источником версионируемой схемы является `DoomRu/Migrations`. При запуске приложение вызывает `Database.MigrateAsync()`: пустая БД получает начальную миграцию `20261016135752_InitialCreate`, при следующих запусках применяются только отсутствующие миграции.

## Что находится в каталоге

| Файл | Назначение |
| --- | --- |
| `schema.sql` | Публичная схема PostgreSQL 17 с записью начальной миграции; без пользователей, телефонов, хешей и токенов |
| `baseline.sql` | Однократная регистрация начальной миграции для существующей эквивалентной схемы, ранее созданной `EnsureCreatedAsync` |

Обычный запуск приложения не требует ручного исполнения этих SQL-файлов: используйте миграции. `schema.sql` подходит для изучения структуры и ручной инициализации отдельной пустой БД. Он создаёт таблицы, индексы и ограничения; поверх существующей схемы его не запускают.

```bash
docker compose exec -T db psql -U doomru -d EMPTY_DATABASE -v ON_ERROR_STOP=1 < database/schema.sql
```

## Переход с EnsureCreated

Существующие таблицы не являются доказательством применённой миграции. Если истории EF нет, обычный `MigrateAsync` попытается создать их повторно.

Перед переходом:

1. Сделайте `pg_dump -Fc` и проверьте, что архив читается.
2. Сравните полную схему с InitialCreate: колонки, типы, nullable, ключи, индексы и связи. Для сравнения можно использовать отдельную БД, созданную новой версией приложения или восстановленную из проверенного архива.
3. Только если схема эквивалентна, выполните baseline:

```bash
docker compose exec -T db psql -U doomru -d doomru -v ON_ERROR_STOP=1 < database/baseline.sql
```

4. Запустите новую версию, проверьте `/health`, вход и историю миграций:

```bash
docker compose exec db psql -U doomru -d doomru -c 'TABLE "__EFMigrationsHistory";'
```

Baseline не создаёт Identity-таблицы и не исправляет расхождения схемы. Его нельзя применять к пустой или неизвестной БД. При несовпадении схемы нужен отдельный план миграции, а не фиктивная запись в истории.

## Предоставленный архив Doomru.sql

Несмотря на расширение `.sql`, файл имеет сигнатуру `PGDMP`: это custom archive `pg_dump` PostgreSQL 16.3. Читать и восстанавливать его нужно `pg_restore`, а не `psql`. В нём есть схема Identity, история InitialCreate и данные аккаунта. Исходный архив хранится приватно; в публичный Git включена только схема без данных.

Пример проверки в отдельной БД на PostgreSQL 17:

```bash
docker compose exec db createdb -U doomru doomru_review
docker compose exec -T db pg_restore -U doomru -d doomru_review \
  --no-owner --no-acl --exit-on-error < /PRIVATE/PATH/Doomru.sql
```

Не используйте `--create` для этого архива: исходная БД создана с Windows locale `Russian_Russia.1251`, которого может не быть в Linux. Создавайте целевую БД заранее с доступной локалью. Не выполняйте `--clean` над рабочей БД без отдельного решения о замене данных. Учётные записи переносятся отдельной проверенной операцией, не через публичные seed-файлы.

## Следующие изменения схемы

Создавайте миграции EF Core из текущей модели, проверяйте SQL и пробный переход на копии БД. Перед production deploy делается бэкап; rollback приложения не отменяет миграции и не восстанавливает данные автоматически. Новая схема должна оставаться совместимой с предыдущей версией приложения до окончания периода возможного отката.
